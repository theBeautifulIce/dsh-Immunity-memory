# 开发说明

本文写给接手这个仓库的人（或下一次会话的 agent）。目标是：打开任意一个源文件之前，
先知道它为什么存在、边界在哪、改哪里安全。

## 1. 形态

这是一个 **DSH 插件包**，不是独立应用：

- **宿主侧**（`index.js` + `lib/*`）跑在 DSH 主进程里，拿到 `ctx`（cordis 上下文）。
- **客户端侧**（`client.js`）跑在 DSH Web GUI 里，由 `window.__ModuleLoader__.load` 加载，
  注册到设置页的 `settings.section` 槽位。
- 两侧**不共享模块**，只通过 HTTP 接口（`/dsh-memory-plugin/api/v2`）通信。

为什么不用 RPC 或 DSH 的 Config 机制：

1. 客户端侧在本环境里没有稳定的 RPC 客户端（`host.call` 的对端没有文档与示例）；
   已装的三个市场插件（terse-mode / mcp-connector / dshmarket）都用 `fetch` + 自己的
   `/xxx/api` 前缀，这是被验证过的路径。
2. 设置项有十几个分组、上百个字段，还要和「记忆库」数据一起读写；用插件自带的 JSON
   存储比塞进 `cordis.patch.yml` 的行 config 更简单，也不会因为用户改了别的插件而互相影响。
   行 config 只在首次启用时作为默认值。

## 2. 数据模型

**默认存 SQLite**（`node:sqlite`，宿主进程自带，零依赖），库文件默认
`~/.dsh/storages/dsh-memory-plugin/memory.sqlite3`。表结构按设计文档 §7.2：

| 表 | 内容 | 关键列 |
| --- | --- | --- |
| `memories` | 记忆主体（含记忆记事本条目） | `id`、`layer`、`type`、`title`、`content`、`metadata`(JSON)、`created_at`、`updated_at`、`last_accessed`、`access_count`、`importance_score`(0–1)、`confidence`、`freshness_period`(秒)、`status` |
| `events` | 日常记事本（事件流水） | `id`、`timestamp`、`event_type`、`title`、`summary`、`content`、`tags`、`importance`、`session_id` |
| `assets` | 资产记事本 | `id`、`asset_type`、`name`、`description`、`sensitivity_level`、`data`、`created_at`、`last_used`、`usage_count`、`tags` |
| `relationships` | 记忆关系（冲突边） | `source_id`、`target_id`、`edge_type`、`weight`，`UNIQUE(source,target,edge)` |
| `changelog` | 记忆记事本 / 操作流水（审计） | `timestamp`、`operation`、`layer`、`target_id`、`reason`、`triggered_by` |
| `config` | 设置与元信息 | `key`、`value`(JSON)、`updated_at` |
| `schema_migrations` | 建表版本 | `version`、`applied_at` |

`memories` 上按设计建了 `(layer, type)`、`created_at`、`importance_score DESC`、`status` 索引；
`relationships` 建了 source/target/edge 索引；`changelog` 建了 timestamp/target 索引。

引擎侧仍然是内存对象 + 落盘（评分要遍历全部条目，几千条以内同步足够快）；
`lib/sqlite.js` 在 `write(state)` 里按**行签名**做增量 upsert / delete，不整库重写：
新增插入、变更 `INSERT … ON CONFLICT DO UPDATE`、消失的删掉，冲突同步到 `relationships`，
审计只追加（被 `compact` 截断时才整表重写）。每次打开库前按 `storage.backupKeep` 轮转
`memory.sqlite3.bak-N`。

**JSON 单文件**（`store.json`）保留为显式可选引擎与运行时回退：设置里
`storage.engine = json`，或宿主缺少 `node:sqlite` 时自动退回。早期版本的数据文件会在
第一次以 SQLite 打开时**自动迁移**进数据库（同目录下存在 `store.json` 就导入，迁移后照常使用）。
JSON 引擎的条目结构：

```jsonc
{
  "version": 1,
  "createdAt": "...", "updatedAt": "...",
  "settings": { /* 见 lib/settings.js */ },
  "items": [ /* 记忆与记事本条目 */ ],
  "audit": [ { "at": "...", "action": "create", "detail": "mem_xxx", "actor": "agent" } ],
  "meta": { "writes": 0, "searches": 0, "lastMaintenance": null, "lastCleanup": null }
}
```

条目（一个 `items[]` / 一行记录）关键字段：

| 字段 | 说明 |
| --- | --- |
| `id` | `mem_` + 12 位随机串 |
| `type` | `memory`（记忆）或 `note`（记事本条目） |
| `layer` | `L0`…`L7`，见 `LAYERS` |
| `notebook` | `memory` / `daily` / `asset`（SQLite 里分别落到 memories / events / assets） |
| `title` / `content` / `tags[]` | 正文内容 |
| `importance` | 1–10（SQLite 里换算成 0–1 的 `importance_score`），影响检索排序与提示词注入顺序 |
| `status` | `active` / `archived` / `expired` / `conflicted` |
| `pinned` | 置顶，跳过自动维护 |
| `ttlDays` / `expiresAt` | 保鲜期（SQLite 里存成 `freshness_period` 秒） |
| `accessCount` / `lastAccessAt` | 每次检索命中累加 |
| `version` / `conflicts[]` / `duplicateOf` | 修订与冲突信息 |
| `source` | `{ kind: 'user'|'agent'|'import', sessionId, workspace }` |

## 3. 引擎行为（`lib/engine.js`）

- **写入门槛**：`enabled` 关闭 → 拒绝；层被关掉 → 拒绝；不可变层（L0/L1/L3）编辑 → 拒绝
  （除非 `write.allowImmutableEdit`）；正文短于 `write.minContentLength` → 拒绝。
- **去重**：新条目与已有条目做 jaccard 相似度，≥ `write.dedupeThreshold` 时仍然写入，
  但在返回值里带 `duplicateOf`，维护任务 `dedupe` 会提示。
- **冲突**：写入 L2 时与同层条目相似度过高（默认 0.82）→ 直接置为 `conflicted`，
  可在界面上「提升 / 归档 / 删除」处理。
- **检索**：`tokenize` 把中文切成单字 + 二元组、英文按词，命中计分后加权：
  `0.55*相关度 + 0.2*重要度 + 0.15*新鲜度 + 0.1*访问频次 + 置顶加成`，
  再乘状态权重（`active 1 / conflicted .85 / archived .6 / expired .4`）。
  默认只搜「可用」条目（active + conflicted），可在界面上切到全部。
- **维护**：`cleanup`（过期）、`archive`（长期未访问）、`dedupe`（重复提示）、
  `reflect`（高频访问条目提升重要度，并给出合并建议）、`compact`（压缩审计日志）。
  定时器按 `maintenance.intervalHours` 跑，`autoRun=false` 时只在界面里手动跑。

## 4. 工具（`lib/tools.js`）

| 工具 | 说明 |
| --- | --- |
| `memory_write` | 写一条记忆（正文必填，可选标题/层/类型/记事本/标签/重要度/保鲜期） |
| `memory_search` | 检索（关键词、层、类型、状态、条数） |
| `memory_get` | 按 id 读一条 |
| `memory_update` | 按 id 改字段 |
| `memory_forget` | 按 id 批量删除 |
| `memory_stats` | 库统计（总数、分层分布、最近写入） |

工具与设置页**调用同一个引擎实例**，所以界面里能看到模型刚写的东西。工具的 `output.render`
统一返回一段文本，避免模型拿到嵌套结构。

## 5. 接口（`lib/api.js`）

`POST /dsh-memory-plugin/api/v2`，body `{ "method": "items.list", "params": { ... } }`，返回

```jsonc
{ "ok": true, "value": { } }                  // 成功
{ "ok": false, "error": { "code": "TOO_SHORT", "message": "…" } }   // 失败
```

方法：`bootstrap`、`status`、`items.list`、`items.search`、`items.get`、`items.create`、
`items.update`、`items.delete`、`items.bulk`、`settings.get`、`settings.save`、`settings.reset`、
`maintenance.run`、`prompt.preview`、`audit.list`、`data.export`、`data.import`。
`GET /dsh-memory-plugin/api/v2/<method>` 作为兜底只支持只读方法（桌面壳的 GET 转发不可靠，
客户端默认也用 POST 空 body 读）。旧前缀 `/memory-plugin/api` 仍会尽力注册一份，供早期
文档里的地址使用；被历史路由占用时静默跳过。

> 路径末段带 `v2`、且**不放在旧前缀下面**是刻意的。`webServer.register()` 对重复的
> `(kind, path)` **直接抛错**，路由的释放只能由注册方发起；插件热重载/重装时上一代的
> prefix 路由可能还活着（它闭包住上一代的引擎，于是设置页会读到旧数据），而 prefix 匹配
> 会把它的所有子孙路径一起吞掉——所以新路径必须是独立的顶层前缀，不能是 `.../api/v2` 这种
> 挂在旧前缀下的地址。同时 `index.js` 把路由挂在 `webServer` 上的 holder 里（`holder.path`
> 记录当前注册的路径），handler 每次通过 `holder.engine` 取当前引擎，两者配合后重装不再串代。
> 出问题时先看 `<数据目录>/plugin.log`，里面按顺序记录了 attach 的每一步。

安全：每个请求校验 Host 头（回环或 DSH 的 trustedHosts）、`sec-fetch-site`、`Origin`，
跨站请求直接 403；body 上限 2MB。

## 6. 客户端页面（`client.js`）

- 注册：`ctx.slots.register({ name: 'settings.section', id: 'memory-plugin', order: 60, label })`。
- 取数：`bootstrap` 一次拿回设置、表单 schema、统计、分层、记事本、审计、存储信息。
- 结构：顶部统计徽章 + 四个 tab（记忆 / 记事本 / 设置 / 维护），记忆与记事本共用
  `ItemBrowser`（左列表右编辑器）。
- 样式：整段 CSS 用 `styles.insert()` 注入，颜色只用 `--dsw-alias-*` 主题变量并带兜底色，
  不写死浅色/深色。
- 兼容：取地址失败时依次尝试 `location.origin`、`document.baseURI`、
  `__DSH_TRANSPORT__.streamBaseUrl`、裸路径；只有连不上（TypeError）才换地址，
  避免把写操作重试成重复写入。

## 7. 测试

```pwsh
node scripts/check.mjs
```

- `tests/engine.test.mjs`：引擎纯逻辑（设置归一化、去重、冲突、检索、维护、导出导入）。
- `tests/tools.test.mjs`：按 `JsonSchemaNode` 契约校验 6 个工具定义，并真的执行一遍，
  检查返回值是无损 JSON 且符合自己声明的 `output.schema`。
- `tests/sqlite.test.mjs`：SQLite 存储层（建表、表列与设计 §7.2 对齐、分表映射、重要性/保鲜期
  换算、冲突关系表、审计流水、增量写入、删除、重开持久化、旧 JSON 迁移）。
- `tests/api.test.mjs`：起一个真实 http server 包住 `mountApi` 的 handler，用 fetch 验证
  全部方法、错误码、Host 伪造拦截。
- `tests/client.render.mjs`：用 profile 里真实的 react + react-dom/server 把设置页与各面板
  渲染成 HTML，捕捉渲染期异常（`client.js` 末尾的 `__internals` 仅供测试使用）。

## 8. 发布 / 更新

1. 改完代码后先跑 `node scripts/check.mjs`。
2. `git add -A && git commit -m "feat: …"`。
3. 在 DSH 里重新 `plugin_manager install_bundle`（同一路径）。已安装的版本需要重启
   DSH 才会换成新代码；只是新装则热生效。
4. 打开设置页验证：列表能读、能写、设置能存、维护能跑。

## 9. 已知限制

- 检索是关键词加权，不是向量语义检索（设计文档里的语义层是可选项，本实现未启用）。
- 关系图谱未实现：冲突与家族关系目前只记在条目的 `conflicts` 字段里。
- 单文件 JSON 适合几千条记忆；量级再大应换成 SQLite（`lib/store.js` 是唯一需要改的边界）。
